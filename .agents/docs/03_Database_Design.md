# AI GitHub Repository Health Monitor
## Database Design Specification
### Version 1.0.0

## 1. Database Objective

Use **PostgreSQL** as the primary relational database.

The database must support:

- Personal-first usage
- Future multi-tenant SaaS
- Public and private repositories
- GitHub App installations
- Repository monitoring
- Scan jobs and results
- Findings
- Configurable health scoring
- AI analysis
- Recommendations
- User-approved actions
- Notifications
- Audit logs
- Historical health trends

Use normalized relational structures for core entities and JSONB only where flexible external/AI data is required.

---

## 3. Core Tables

### users

Stores application users.

Important fields:

```text
id
email
name
avatar_url
created_at
updated_at
last_login_at
status
```

Use UUID as the application-level primary key.

Email must be unique.

Do not store GitHub access tokens directly in this table.

---

### workspaces

Represents the ownership boundary for SaaS readiness.

Important fields:

```text
id
name
slug
owner_user_id
created_at
updated_at
```

A user should be able to own or belong to a workspace.

All user-owned application resources must ultimately belong to a workspace.

---

### workspace_members

Supports future multi-user collaboration.

Important fields:

```text
id
workspace_id
user_id
role
created_at
```

Roles should initially support:

```text
OWNER
ADMIN
MEMBER
VIEWER
```

Use a unique constraint on `(workspace_id, user_id)`.

---

### github_installations

Stores GitHub App installation metadata.

Important fields:

```text
id
workspace_id
github_installation_id
github_account_id
github_account_login
account_type
permissions_snapshot
status
installed_at
updated_at
```

`github_installation_id` must be unique.

Do not store unnecessary OAuth/PAT credentials.

If credentials/tokens are required by the implementation, store them using an appropriate encrypted/secret-management strategy rather than plain text.

---

### repositories

Stores repositories available to the application.

Important fields:

```text
id
workspace_id
github_installation_id
github_repository_id
owner_login
name
full_name
description
default_branch
is_private
is_archived
is_fork
html_url
monitoring_enabled
last_scanned_at
created_at
updated_at
```

Use the GitHub repository ID as an external identifier.

Create a uniqueness constraint preventing duplicate repository records within the relevant GitHub installation/workspace.

---

## 4. Scan Tables

### scans

Represents every repository scan.

Important fields:

```text
id
repository_id
scan_type
trigger_type
status
started_at
completed_at
error_message
created_at
```

Example `scan_type`:

```text
FULL
INCREMENTAL
TARGETED
```

Example `trigger_type`:

```text
MANUAL
WEBHOOK
SCHEDULED
SYSTEM
```

Example status:

```text
QUEUED
RUNNING
COMPLETED
FAILED
CANCELLED
```

A scan must have a traceable lifecycle.

---

### scan_metrics

Stores measurable results generated by analyzers.

Important fields:

```text
id
scan_id
category
metric_name
metric_value
metric_unit
metadata
created_at
```

Use JSONB `metadata` for analyzer-specific supporting information.

---

## 5. Findings

### findings

Stores repository-health problems detected during scans.

Important fields:

```text
id
repository_id
first_scan_id
last_scan_id
category
severity
title
description
evidence
detection_source
status
fingerprint
first_detected_at
last_detected_at
resolved_at
created_at
updated_at
```

`detection_source` should distinguish:

```text
PROGRAMMATIC
GITHUB
AI
HYBRID
```

Use a stable `fingerprint` to identify recurring findings across scans and prevent duplicate records.

Finding status should support:

```text
OPEN
ACKNOWLEDGED
RESOLVED
IGNORED
```

## 6. Health Scoring Tables

### scoring_configurations

Stores configurable scoring rules.

Important fields:

```text
id
workspace_id
name
is_default
version
created_at
updated_at
```

### scoring_weights

Stores category weights.

Important fields:

```text
id
scoring_configuration_id
category
weight
```

The total active weight must equal **100**.

Never overwrite historical scoring configurations that have already been used. Create a new version instead.

---

### health_scores

Stores the calculated score for every completed scan.

Important fields:

```text
id
repository_id
scan_id
scoring_configuration_id
overall_score
created_at
```

### health_score_categories

Stores category-level scores.

Important fields:

```text
id
health_score_id
category
raw_score
weight
weighted_score
created_at
```

This allows the application to explain exactly how an overall score was produced.

## 10. Audit Logs

### audit_logs

Records security-sensitive and important application actions.

Important fields:

```text
id
workspace_id
user_id
action
resource_type
resource_id
metadata
ip_hash_or_safe_identifier
created_at
```

Audit logs should capture events such as:

- GitHub installation
- Repository added/removed
- Scan triggered
- Configuration changed
- Recommendation approved/rejected
- AI action executed
- Permission-sensitive operations

Do not store raw secrets or sensitive tokens in audit logs.

## 11. Relationships and Integrity

Use foreign keys for all core relationships.

Important relationships:

```text
users → workspaces
workspaces → workspace_members
workspaces → github_installations
github_installations → repositories
repositories → scans
scans → scan_metrics
repositories → findings
scans → health_scores
health_scores → health_score_categories
repositories → ai_analyses
findings → recommendations
recommendations → ai_actions
workspaces → notifications
workspaces → audit_logs
```

Use indexes on frequently queried fields including:

```text
workspace_id
repository_id
github_repository_id
github_installation_id
scan status
scan created_at
finding status
finding severity
health score created_at
notification user_id
```

---

## 12. Database Rules

1. PostgreSQL is the source of truth for application data.
2. Use UUIDs for internal primary keys.
3. Use GitHub IDs as external identifiers.
4. Use UTC timestamps.
5. Use foreign keys and database constraints for integrity.
6. Use transactions for multi-table state changes.
7. Use JSONB only for flexible metadata, external payloads, and AI results.
8. Never store plaintext secrets.
9. Preserve historical scan and scoring data.
10. Never modify historical scores when configuration changes.
11. Prevent duplicate webhook/scan processing through unique identifiers or idempotency records.
12. Design queries and indexes for multi-tenant filtering.
13. Every workspace-owned resource must enforce workspace isolation.
14. Use database migrations for schema changes.
15. Avoid destructive schema changes without migration and rollback planning.

The database schema must remain consistent with the system architecture, health-scoring model, security architecture, API design, and automation workflow defined in subsequent specifications.
